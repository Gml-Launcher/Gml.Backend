# Разработка GML Manager

`gml-manager.sh` — standalone-установщик Gml.Backend для Linux. Пользователь
может скачать один файл и сразу передать его в `sh`, поэтому установщик не
должен зависеть от исходных модулей во время выполнения:

```sh
curl -sSL https://raw.githubusercontent.com/Gml-Launcher/Gml.Backend/refs/heads/master/installer/gml-manager.sh | sudo sh
```

Чтобы большой shell-скрипт было проще развивать и проверять, его исходный код
разделён на модули в `gml-manager-src/`. Файл `gml-manager.sh` автоматически
собирается из этих модулей и хранится в Git как готовый публичный артефакт.

> Не редактируйте `gml-manager.sh` вручную. Любое такое изменение будет потеряно
> при следующей сборке. Вносите изменения в `gml-manager-src/`, после чего
> запускайте builder.

## Быстрый цикл разработки

Все команды ниже выполняются из корня репозитория.

1. Измените нужный модуль в `installer/gml-manager-src/`.
2. Соберите standalone-скрипт:

   ```sh
   sh installer/build-gml-manager.sh
   ```

3. Запустите быстрые проверки:

   ```sh
   sh installer/build-gml-manager.sh --check
   sh installer/tests/gml-manager-unit.sh
   sh -n installer/gml-manager.sh
   git diff --check
   ```

4. Просмотрите изменения как в исходном модуле, так и в сгенерированном
   `installer/gml-manager.sh`. В коммит должны попасть оба файла.

## Почему generated-файл хранится в Git

Документированные команды установки скачивают `installer/gml-manager.sh`
напрямую через raw GitHub URL. Если хранить в репозитории только модули, такой
способ установки перестанет работать или потребует отдельного release pipeline.

Поэтому в репозитории находятся одновременно:

- небольшие исходные модули, с которыми работает разработчик;
- builder, задающий порядок сборки;
- готовый `gml-manager.sh`, который скачивает пользователь;
- проверка CI, запрещающая коммитить устаревший generated-файл.

## Структура модулей

Порядок модулей объявлен в переменной `MODULES` внутри
`build-gml-manager.sh`. Builder всегда объединяет их в этом порядке.

### `00-config.sh`

Содержит значения по умолчанию, URL удалённых ресурсов и глобальное состояние
текущего запуска: действие, каталог установки, версию, режим прокси, домен,
порты и язык интерфейса.

Этот модуль загружается первым. Добавляйте сюда только инициализацию переменных,
не выполняющую сетевые запросы, установку пакетов или другие внешние действия.

### `10-i18n.sh`

Содержит русские и английские сообщения, определение языка, banner, справку
`--help` и единый вывод ошибок.

### `20-cli.sh`

Отвечает за:

- разбор команд `install`, `update`, `delete` и их параметров;
- интерактивные вопросы;
- подтверждение замены управляемого Compose-файла;
- выбор версии GML;
- разрешение итогового режима прокси и связанных параметров.

Разбор аргументов должен завершаться до привилегированных или изменяющих систему
операций. Новые CLI-параметры также необходимо добавить в справку обоих языков
и покрыть unit-тестом.

### `30-network.sh`

Содержит проверки домена, TCP-портов и IP-адресов, обращения к публичным
DNS-over-HTTPS resolver и проверки требований режима `global`.

Функции этого модуля должны возвращать ненулевой код при ошибке и печатать диагностику в stderr.

### `40-system.sh`

Содержит проверку root, выполнение шагов со spinner, определение ОС, установку
пакетов и подготовку Docker с Compose plugin.

Учитывайте различия имён пакетов между `apt`, `apk`, `dnf`, `yum`, `zypper` и
`pacman`. Установка должна оставаться неинтерактивной там, где это поддерживает
пакетный менеджер.

### `50-files.sh`

Работает с каталогом установки и `.env`: создаёт каталоги, загружает Compose,
генерирует `SECURITY_KEY`, читает и обновляет управляемые ENV-переменные.

### `60-compose.sh`

Содержит Compose wrappers, проверку итоговой конфигурации, ожидание ACME-сертификата и транзакционное обновление стека.

Перед остановкой работающего стека новая конфигурация проверяется, а образы загружаются заранее. Если новый стек не запускается, функция обновления восстанавливает предыдущие `docker-compose.yml` и `.env`, затем пытается снова запустить старую версию.

### `70-commands.sh`

Собирает высокоуровневые сценарии `install`, `update` и `delete` из функций предыдущих модулей. Здесь же находятся итоговые сообщения с URL панели и логика резервного копирования удаляемой установки.

### `99-main.sh`

Содержит точку входа `main` и guard, предотвращающий запуск установки при подключении `gml-manager.sh` в unit-тесте.:

```sh
if [ "${GML_MANAGER_SKIP_MAIN:-0}" != "1" ]; then
    main "$@"
fi
```

## Как работает builder

`build-gml-manager.sh` написан на POSIX `sh`. Для сборки нужны стандартные утилиты `sed`, `mktemp`, `cmp`, `chmod` и `mv`.

Обычный запуск:

```sh
sh installer/build-gml-manager.sh
```

Builder выполняет следующие действия:

1. Проверяет наличие всех модулей из явного списка `MODULES`.
2. Проверяет синтаксис каждого модуля через `sh -n`.
3. Создаёт временный файл рядом с целевым скриптом.
4. Записывает shebang и предупреждение о generated-файле.
5. Последовательно добавляет содержимое модулей.
6. Проверяет синтаксис полностью собранного временного файла.
7. Устанавливает права `0755`.
8. Атомарно заменяет `installer/gml-manager.sh` через `mv`.

Временный файл удаляется при штатном завершении и при сигналах завершения.

### Режим проверки

```sh
sh installer/build-gml-manager.sh --check
```

В этом режиме builder проверяет синтаксис модулей и собранного временного файла, затем сравнивает результат с закоммиченным `gml-manager.sh` и ничего не перезаписывает. Проверка завершается с ошибкой, если синтаксис некорректен, содержимое отличается, generated-файл отсутствует или у него нет права на выполнение.

Сообщение:

```text
Generated installer/gml-manager.sh is out of date. Run installer/build-gml-manager.sh.
```

означает, что после изменения модулей нужно снова выполнить обычную сборку и добавить обновлённый generated-файл в коммит.

## Тестирование

### Unit- и mock-проверки

```sh
sh installer/tests/gml-manager-unit.sh
```

Тест подключает именно собранный `installer/gml-manager.sh`, а не отдельные модули. Это гарантирует, что проверяется тот же файл, который получает пользователь. `GML_MANAGER_SKIP_MAIN=1` предотвращает настоящий запуск установщика.

Сценарий проверяет:

- выбор языка и локализованное предупреждение;
- подтверждение и отмену обновления;
- разбор CLI-параметров;
- проверку FQDN и диапазона портов;
- разбор ответа DNS-over-HTTPS;
- совместимость обновления старой установки без proxy ENV;
- порядок `pull` перед `down`;
- восстановление старых Compose и `.env` после имитации ошибки нового стека.

Сообщение `New proxy mode failed; restoring the previous installation` во время этого теста ожидаемо: тест намеренно вызывает ошибку запуска, чтобы проверить rollback.

## Проверки CI

Workflow `.github/workflows/gml-manager-tests.yml` запускается при изменении generated-файла, builder, исходных модулей, тестов, ENV-шаблона или установочного Compose-файла.

В начале job CI:

1. Запускает builder с `--check`.
2. Выполняет сборку дважды и сравнивает checksum результатов.
3. Проверяет отсутствие diff после генерации.
4. Проверяет executable mode и синтаксис всех shell-файлов.
5. Запускает unit/mock-тест.

После быстрых проверок сохраняется существующая матрица Ubuntu x64/ARM64, которая выполняет настоящие `install`, `update` и `delete` с Docker-образами.

## Добавление нового модуля

Если существующие области ответственности не подходят для новой логики:

1. Создайте файл с числовым префиксом в `installer/gml-manager-src/`.
2. Добавьте его имя в `MODULES` внутри `build-gml-manager.sh` в нужной позиции.
3. Не добавляйте shebang: он создаётся builder один раз для итогового файла.
4. Не запускайте действия на верхнем уровне модуля. Оставляйте там определения функций; исключения — инициализация в `00-config.sh` и guard в `99-main.sh`.
5. Пересоберите `gml-manager.sh` и выполните все быстрые проверки.

Числовой префикс помогает читать структуру, но фактический порядок определяет только список `MODULES`. Builder намеренно не подключает новые `*.sh` автоматически, чтобы случайный файл не попал в публичный установщик.

## Правила совместимости

- Сохраняйте POSIX-совместимый синтаксис `/bin/sh`. Не используйте массивы, `[[ ... ]]`, `source`, `function name` и другие Bash-specific конструкции.
- Не меняйте путь `installer/gml-manager.sh`: он является публичным URL.
- Сохраняйте поддержку запуска через pipe, где исходные модули отсутствуют.
- Помните, что переменные функций в POSIX `sh` глобальны, если shell не
  поддерживает расширение `local`. Используйте достаточно специфичные имена для временных переменных, особенно в транзакционной логике.
- Не заявляйте успешный ACME или Docker E2E по результатам только `sh -n`, unit-теста или `docker compose config`.

## Диагностика

### Generated-файл устарел

Запустите:

```sh
sh installer/build-gml-manager.sh
sh installer/build-gml-manager.sh --check
```

Затем добавьте в коммит изменённый модуль и `installer/gml-manager.sh`.

### Builder сообщает об отсутствующем модуле

Проверьте список `MODULES`. Каждый перечисленный файл должен существовать в
`installer/gml-manager-src/`. Если модуль был переименован, обновите manifest и
пересоберите установщик.

### Unit-тест проходит, но CI install/update/delete падает

Unit-тест использует mock-функции и не проверяет доступ к Docker registry, совместимость конкретного Docker-образа, занятость реальных портов, публичный DNS или выпуск ACME-сертификата. Для причины ошибки смотрите журнал соответствующего шага полной CI-матрицы и логи Compose.
